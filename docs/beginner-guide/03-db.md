In words:

- **users** have many **sessions** (one per login/device); each session has **refresh_tokens** (chapter 10).
- A **venue** has **venue_sections**, which have **venue_seats**. This is the *physical* building: seat "Balcony, row C, seat 12" at grid position x=11, y=24. It never changes.
- An **event** happens at a venue and is organised by a user.
- **event_seats** has **one row per seat per event**, copied from `venue_seats` when the event is created, with its own **price**, **status** (`available`, `held`, `booked`), **booking_id** (who holds it) and **version** (a counter bumped on every change).
- A **booking** belongs to a user and an event, has a status (`pending`, `confirmed`, `expired`, `cancelled`, `refunded`) and an `expires_at` time. Its seats are listed in **booking_items**.
- A booking has **payments**; a payment can have **refunds**; a confirmed booking has one **ticket** per seat.

<div class="tip"><b>Why copy venue seats into event_seats?</b> The venue is a template. Each event sells its own inventory with its own prices. Booking a seat for Friday's concert must not touch Saturday's. Separating "the template" from "the stock" is a pattern you will reuse (products vs. inventory, courses vs. enrolments, and so on).</div>

## Migrations: how tables are created

You never create tables by hand. You write **migrations**: numbered files that change the database structure step by step. They live in `src/db/migrations/`:

```text
0001_initial_schema.ts        users, venues, seats, events, event_seats
0002_auth.ts                  passwords, sessions, refresh tokens, reset tokens
0003_bookings.ts              bookings, booking_items, seat holders
0004_jobs_tickets_posters.ts  outbox, notifications, tickets, poster columns
0005_payments.ts              payments, refunds, webhook_events, idempotency_keys
0006_outbox_notify_immediate_only.ts   a performance fix found by load testing
```

Each file has an `up` function (apply the change) and a `down` function (undo it). Kysely's migrator remembers which ones already ran (in its own `kysely_migration` table), so `npm run migrate` only applies new ones. The rule written at the top of `0001`: **never edit a migration that has already run anywhere; add a new one instead.** That's how every developer's database, the test database and production end up with the same structure.

Here is part of `0001_initial_schema.ts`. The SQL is written by hand on purpose:

```sql
CREATE TYPE event_status AS ENUM ('draft', 'published', 'cancelled');

CREATE TABLE events (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organizer_id uuid NOT NULL REFERENCES users (id) ON DELETE RESTRICT,
  venue_id     uuid NOT NULL REFERENCES venues (id) ON DELETE RESTRICT,
  title        text NOT NULL CHECK (char_length(title) BETWEEN 1 AND 200),
  status       event_status NOT NULL DEFAULT 'draft',
  starts_at    timestamptz NOT NULL,
  ends_at      timestamptz NOT NULL,
  search       tsvector GENERATED ALWAYS AS (
                 setweight(to_tsvector('english', title), 'A') ||
                 setweight(to_tsvector('english', description), 'B')
               ) STORED,
  CHECK (ends_at > starts_at),
  CONSTRAINT events_no_venue_overlap EXCLUDE USING gist (
    venue_id WITH =,
    tstzrange(starts_at, ends_at) WITH &&
  ) WHERE (status <> 'cancelled')
);
CREATE INDEX events_listing_idx ON events (status, starts_at, id);
CREATE INDEX events_search_idx ON events USING gin (search);
```

Piece by piece:

- `CREATE TYPE ... AS ENUM` makes a type that only allows those exact values. The database will reject `status = 'publishd'` (typo).
- `uuid PRIMARY KEY DEFAULT gen_random_uuid()`: every event gets a random unique id automatically.
- `REFERENCES users (id)` is a **foreign key**: `organizer_id` must be an id that exists in `users`. `ON DELETE RESTRICT` means you cannot delete a user who organises events.
- `CHECK (...)`: a rule checked on every insert/update. An event can't end before it starts, whatever the code does.
- `search ... GENERATED ALWAYS AS (...) STORED`: a column Postgres computes itself from title and description, used for full-text search ("rock concert" finds "Rock Night Concert").
- `EXCLUDE USING gist (...)`: **no two non-cancelled events at the same venue may overlap in time**. `&&` means "ranges overlap". This is enforced by the database even when two organisers submit at the exact same moment. A check in application code ("SELECT any overlapping event, then INSERT") would have a race: both could check before either inserts.
- `CREATE INDEX ...`: an index is like a book's index; it makes lookups fast. `events_listing_idx` exactly matches the main listing query "published events, ordered by start time".

The table below lists the rules the database enforces. Learning to push rules into the database is one of the most valuable lessons of this project:

| Rule | Enforced by |
|---|---|
| No two events overlap at a venue | `EXCLUDE` constraint (above) |
| A seat is `available` exactly when no booking points at it | `CHECK ((status = 'available') = (booking_id IS NULL))` |
| One active hold per user per event | partial unique index on `bookings (user_id, event_id) WHERE status = 'pending'` |
| One valid ticket per seat | partial unique index on `tickets (event_seat_id) WHERE status = 'valid'` |
| A webhook is processed once | primary key `(provider, event_id)` on `webhook_events` |
| At most one live refund per payment | partial unique index on `refunds` |

A **partial unique index** is a uniqueness rule that only applies to some rows. "Unique `(user_id, event_id)` *where* status is pending" means a user can have many old bookings for an event, but only one pending hold at a time.

## Table types for TypeScript (`src/db/types.ts`)

Kysely needs to know the shape of each table to type-check queries. `types.ts` describes them in TypeScript:

```ts
export const USER_ROLES = ['attendee', 'organizer', 'admin'] as const;
export type UserRole = (typeof USER_ROLES)[number];   // 'attendee' | 'organizer' | 'admin'

export interface UsersTable {
  id: Generated<string>;            // the database generates it; optional on insert
  email: string;
  name: string;
  role: Generated<UserRole>;        // has a default
  passwordHash: string | null;
  createdAt: CreatedAt;             // set by the database, never by us
  updatedAt: UpdatedAt;             // maintained by a trigger
}
```

Notice `passwordHash` in camelCase while the column is `password_hash`. The `CamelCasePlugin` (next section) translates automatically. The `as const` array trick gives you both a list you can loop over (for Zod enums) and a type.

## Connecting: the pool (`src/db/index.ts`)

```ts
pg.types.setTypeParser(pg.types.builtins.INT8, (v) => Number(v));

export const pool = new pg.Pool({
  connectionString: config.DATABASE_URL,
  max: config.DB_POOL_MAX,                          // at most N connections at once
  connectionTimeoutMillis: config.DB_CONNECT_TIMEOUT_MS, // wait max 5 s for a free one
  idleTimeoutMillis: 30_000,
  statement_timeout: config.DB_STATEMENT_TIMEOUT_MS,     // Postgres kills queries > 15 s
  idle_in_transaction_session_timeout: 30_000,           // and forgotten transactions
  application_name: 'ticket-mng',
});

export const db = new Kysely<DB>({
  dialect: new PostgresDialect({ pool }),
  plugins: [new CamelCasePlugin()],
});
```

- Opening a database connection is slow, so apps keep a **pool** of open connections and lend them out. `max` limits how many run at once. If all are busy, a request waits; if it waits longer than `connectionTimeoutMillis`, it fails, and the error handler turns that into `503 SERVICE_BUSY` ("try again shortly") instead of hanging forever.
- The timeouts are **safety nets**: a runaway query or a transaction someone forgot to finish (holding locks!) is cut off by Postgres itself.
- `db` is the object every file imports to run queries.
- The first line: Postgres big integers (`bigint`, `count(*)`) come back as text by default; this converts them to JavaScript numbers.

## Writing queries with Kysely

Kysely reads almost like SQL:

```ts
// SELECT id, email, name, role, created_at FROM users WHERE id = $1
const user = await db
  .selectFrom('users')
  .select(['id', 'email', 'name', 'role', 'createdAt'])
  .where('id', '=', currentUser(req).id)
  .executeTakeFirst();             // one row or undefined
```

```ts
// UPDATE users SET name = $1 WHERE id = $2 RETURNING ...
const user = await db
  .updateTable('users')
  .set({ name: req.body.name })
  .where('id', '=', currentUser(req).id)
  .returning(userColumns)
  .executeTakeFirst();
```

The values (`$1`, `$2`) are sent separately from the SQL text, which prevents **SQL injection** (a user typing `'; DROP TABLE users; --` as their name does nothing bad). When a query is clearer in raw SQL, the code uses the `sql` tag, which is still safe because `${...}` values become parameters:

```ts
await sql`
  INSERT INTO venue_seats (section_id, row_label, seat_number, x, y)
  SELECT * FROM unnest(
    ${seats.map((s) => sectionId.get(s.section))}::uuid[],
    ${seats.map((s) => s.rowLabel)}::text[],
    ${seats.map((s) => s.seatNumber)}::int[],
    ${seats.map((s) => s.x)}::int[],
    ${seats.map((s) => s.y)}::int[]
  )
`.execute(trx);
```

This inserts thousands of seats in **one** statement: it sends five arrays and `unnest` turns them into rows. Inserting 50,000 seats one by one would mean 50,000 network round trips.

## Transactions (`src/db/transaction.ts`)

A transaction groups changes so they all happen or none do. Kysely's basic form:

```ts
const venue = await db.transaction().execute(async (trx) => {
  const venue = await trx.insertInto('venues').values({...}).returningAll().executeTakeFirstOrThrow();
  await trx.insertInto('venueSections').values(...).execute();
  await sql`INSERT INTO venue_seats ...`.execute(trx);
  return venue;
});
```

Inside the callback you use `trx` instead of `db`. If any line throws, everything is rolled back: you never get a venue with half its seats.

This project wraps it in a smarter helper, `withTransaction`:

```ts
const RETRYABLE = new Set([
  '40001', // serialization_failure
  '40P01', // deadlock_detected
]);

export async function withTransaction<T>(
  fn: (trx: Transaction<DB>) => Promise<T>,
  { isolation = 'read committed', retries = 3 }: TransactionOptions = {},
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    const effects: Effect[] = [];
    try {
      const result = await pendingEffects.run(effects, () =>
        db.transaction().setIsolationLevel(isolation).execute(fn),
      );
      await runEffects(effects);        // run "after commit" effects
      return result;
    } catch (err) {
      if (!isRetryable(err) || attempt >= retries) throw err;
      await sleep(Math.random() * 10 * 2 ** attempt);   // jittered backoff, then retry
    }
  }
}
```

Two extra features:

1. **Automatic retry.** Under heavy concurrency, Postgres sometimes aborts a transaction on purpose, with a *deadlock* (two transactions waiting for each other) or a *serialization failure* (in the strictest isolation mode, it detected that two transactions conflicted). Nothing is wrong with the request; running it again works. So the helper retries up to 3 times, waiting a small random time (*jitter*) so retries don't collide again.
2. **After-commit effects.** Some things must happen only *after* the data is really saved: telling live seat maps "this seat is now held", or clearing caches. If you did them inside the transaction and it then rolled back, viewers would see a seat change that never happened.

```ts
export function afterCommit(effect: Effect): void {
  const effects = pendingEffects.getStore();
  if (effects) effects.push(effect);       // inside a transaction: remember it for later
  else void runEffects([effect]);          // outside: run now
}
```

`pendingEffects` is an `AsyncLocalStorage`: a Node feature that works like a variable scoped to "this chain of async calls". Any code deep inside the transaction can call `afterCommit(...)` without being passed anything, and the effect is attached to the *current* transaction. Only the attempt that commits runs its effects.

<div class="warn"><b>A rule this code follows everywhere:</b> never call external services (send email, call the payment provider) <i>inside</i> a transaction. The transaction may be retried (the email would be sent twice) or rolled back (the email would describe something that didn't happen), and it holds locks while waiting on the network. Use <code>afterCommit</code> for best-effort effects and the <b>outbox</b> (chapter 13) for things that must happen.</div>

# The journey of one request

Let's follow `POST /api/v1/events/:id/bookings` (hold seats) through the system. This table is the map of the whole backend:

| Step | Where | What happens |
|---|---|---|
| 1 | Nginx | Decrypts HTTPS, applies an edge rate limit, adds `X-Request-Id`, picks the API copy with the fewest active connections. |
| 2 | `app.ts` (`genReqId`) | Adopts the request id (or makes one). Every log line of this request carries it. |
| 3 | `onRequest` hooks | Metrics: "one more in flight". Opens the request context so deep code can read the request id. Per-IP rate limit in Redis. |
| 4 | `auth/guard.ts` | Checks the access token, checks the session isn't revoked, sets `req.user`. |
| 5 | Zod schema | Validates `:id` and the body. Bad input never reaches the handler (400). |
| 6 | `bookings/routes.ts` | Per-user rate limit on holds; handles `Idempotency-Key` (safe retries). |
| 7 | `bookings/service.ts` | The business logic: checks, claim gate, transaction, lock seats, create the booking. |
| 8 | Kysely + pool | Borrows one connection for the transaction; fails fast with 503 if none is free in 5 s. |
| 9 | Serialization | The response schema decides which fields leave the server. |
| 10 | `onResponse` / `onSend` | Records the request duration; adds `x-request-id` and `x-served-by` headers. |

A typical route definition shows steps 4, 5 and 9 in one place:

```ts
app.post(
  '/events/:id/bookings',
  {
    onRequest: requireAuth,                         // step 4: must be logged in
    schema: {
      tags: ['bookings'],                           // for the /docs page
      summary: 'Hold seats (creates a pending booking)',
      security: bearerAuth,
      params: IdParams,                             // step 5: :id must be a UUID
      headers: z.object({ 'idempotency-key': z.string().optional() }),
      body: z.object({
        seatIds: z.array(z.int().positive()).min(1).max(50)
          .refine((ids) => new Set(ids).size === ids.length, 'Seat ids must be unique'),
      }),
      response: { 201: BookingDto, ...errors, 429: ErrorResponse },   // step 9
    },
  },
  async (req, reply) => {                            // step 6-7: the handler
    const user = currentUser(req);
    await enforce(req, reply, [[HOLD_LIMIT, user.id]]);
    return withIdempotency(req, reply, user.id, async () => {
      const { bookingId } = await holdSeats(
        { userId: user.id, eventId: req.params.id, seatIds: req.body.seatIds },
        app.bookingOptions,
      );
      reply.header('location', `/api/v1/bookings/${bookingId}`);
      return { statusCode: 201, body: await getBookingFor(user, bookingId) };
    });
  },
);
```

Notice how **short** the handler is. All the thinking lives in `holdSeats` (the service). The route only connects HTTP to business logic.

<div class="tip"><b>The response schema is a security feature.</b> Because Fastify serializes the response through the Zod schema, only declared fields are sent. Even if a handler accidentally returned a whole database row including <code>password_hash</code>, it would not leave the server. The code also converts rows to explicit "DTOs" (data transfer objects) like <code>toUserDto</code> for the same reason.</div>

# Validation and errors

## Validation with Zod

Any data coming from outside is untrusted. Zod checks it at the door. From `auth/routes.ts`:

```ts
body: z.object({
  email: z.email().max(254),
  password: Password,                                  // z.string().min(8).max(128)
  name: z.string().trim().min(1).max(100),
  role: z.enum(['attendee', 'organizer']).default('attendee'),  // no "admin" from the public
}),
```

If someone sends `{"email": "nope", "password": "123"}`, the handler never runs; the client gets:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Invalid request body",
  "details": [ { "path": "body.email", "message": "Invalid email address" },
               { "path": "body.password", "message": "Use at least 8 characters" } ] } }
```

Complex rules use `.refine` / `.superRefine`, like "section names must be unique" or "endsAt must be after startsAt" (see `events/schemas.ts` and `venues/routes.ts`).

## One error shape (`src/lib/errors.ts`)

Every error response in the app has the same shape: `{ "error": { "code", "message", "details?" } }`. Clients branch on `code` (stable), and `message` is for humans.

The code defines an error class and small helper functions:

```ts
export class AppError extends Error {
  constructor(
    readonly statusCode: number,
    readonly code: string,
    message: string,
    readonly details?: unknown,
  ) {
    super(message);
  }
}

export const notFound = (resource: string) => new AppError(404, 'NOT_FOUND', `${resource} not found`);
export const conflict = (code: string, message: string, details?: unknown) =>
  new AppError(409, code, message, details);
```

So anywhere in the code you can write `throw notFound('Event')` or `throw conflict('SEATS_UNAVAILABLE', 'Some seats are no longer available', { seatIds })`, and the **central error handler** converts it into a response. Handlers never build error responses themselves.

The error handler (`errorHandler`) is a chain of "what kind of error is this?":

1. **Zod validation error** → 400 `VALIDATION_ERROR` with per-field details.
2. **`AppError`** → its own status and code (401s also get a `WWW-Authenticate` header).
3. **Postgres constraint error**, mapped by the Postgres error code:

```ts
const PG_ERRORS = {
  '23505': { status: 409, code: 'DUPLICATE', ... },          // unique violation
  '23503': { status: 409, code: 'REFERENCE_CONFLICT', ... }, // foreign key
  '23P01': { status: 409, code: 'EXCLUSION_CONFLICT', ... }, // e.g. overlapping events
  '23514': { status: 422, code: 'CONSTRAINT_VIOLATION', ... }, // CHECK failed
};
```

   This is the "database as the last safety net" idea: even if a handler forgot a check, the constraint fires and the client gets a clean 4xx instead of a 500.

4. **Deadlock / serialization failure** that survived retries → 503 `TRANSIENT_CONFLICT` with `Retry-After: 1`.
5. **Pool timeout or statement timeout** → 503 `SERVICE_BUSY` with `Retry-After: 2`. Overload is not a bug; the client should back off.
6. Fastify's own client errors (bad JSON, body too large) → a stable code.
7. Anything else → logged as a bug, and the client sees a generic 500 `INTERNAL_ERROR` (never the stack trace, which could leak internals).

<div class="tip"><b>Lesson: centralise error handling.</b> Throw meaningful errors from anywhere; convert them to HTTP in exactly one place. Your handlers stay clean, and every error looks the same to clients.</div>
